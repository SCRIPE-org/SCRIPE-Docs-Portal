How does SCRIPE isolate production and development database seeding across all 19 modules?

Long image

A

Answer

SCRIPE enforces a fail-closed, two-tier seeding architecture. DatabaseSeeder (the sole IHostedService) runs idempotent Tier 1 Production Baseline IModuleSeeder classes, while DevDataSeederRunner runs Tier 2 Development UAT seeders only in authorized non-production environments.1

  1. Production baseline seeders sync permissions, menus, features, editions, compliance rules, and system roles idempotently.1
  2. SeedingEnvironmentGuard fails closed whenever Production or Prod appears in host or process environment variables, rejecting --seed-dev, --seed-reset, and config overrides.2
  3. Entitlements, Compliance, Communication, and Plugins no longer register duplicate IHostedService instances; DatabaseSeeder respects SeedDatabase:Enabled: false before running migrations.3
  4. DatabaseSeeder and SeedingExtensions propagate relational migration and seeder failures cleanly and set a non-zero CLI exit code (1).4

How do startup and CLI seeding execute end to end?

Diagram structure

  • Prod guard + enabled? cli-check
  • Set SeedingScope scope-begin
  • Sync Identity core core-sync
  • Run targeted modules module-seeders
  • Non-prod dev opt-in? dev-gate
  • Run 17 dev DAG dev-runner
  • Exit 0/1 or serve host-exit
  • cli-check → scope-begin · enabled
  • core-sync → module-seeders · next
  • dev-gate → dev-runner · authorized
  • dev-gate → host-exit · skipped
  • dev-runner → host-exit · done
  • module-seeders → dev-gate · done
  • schema-init → cli-check · ready
  • scope-begin → core-sync · quiet

Program.cs initializes schemas, delegates --seed CLI runs through ExecuteCliSeedModeAsync (which exits 0 or 1 without starting Kestrel), and otherwise runs DatabaseSeeder as the sole seeding IHostedService.4

  1. Init schemas ↗

    InitializeDatabaseSchemasAsync() creates module schemas and outbox or inbox tables before Kestrel or seeding runs.

  2. Prod guard + enabled? ↗

    SeedingEnvironmentGuard rejects --seed-dev or --seed-reset in Production; normal boot skips migrations and seeders when SeedDatabase:Enabled is false.

  3. Set SeedingScope ↗

    SeedingScope.Begin() sets AsyncLocal<bool> so BaseDbContext and AuditableEntityInterceptor suppress outbox and audit floods.

  4. Sync Identity core ↗

    DatabaseSeeder runs Identity migrations, Guardian triggers, Permissions, Roles, SEC-10 Admin, Workspaces, Menus, Themes, and Presets (when unscoped or targeting Identity).

  5. Run targeted modules ↗

    RunModuleSeedersAsync validates --seed-module, executes registered IModuleSeeder instances sorted by (Order, ModuleName), and propagates any error.

  6. Non-prod dev opt-in? ↗

    RunDevSeedersIfRequestedAsync enforces the Development/Local/UAT/Testing allowlist via SeedingEnvironmentGuard before accepting --seed-dev or SeedDatabase:SeedDevData.

  7. Run 17 dev DAG ↗

    DevDataSeederRunner runs all 17 active Scoped dev seeders from Order 10 to 160 using deterministic UUID v4 IDs from DevSeedConstants.

SCRIPE separates IModuleSeeder (single-method production baseline) from IModuleDevDataSeeder (development UAT datasets), eliminating the dead SeedDevAsync method from IModuleSeeder.1

Which modules seed production data versus dev UAT data?

All 19 backend modules provide an IModuleSeeder (Identity host + 18 registered IModuleSeeder services), while 17 active modules register IModuleDevDataSeeder (Marketplace and Plugins remain business-deferred). All IModuleDevDataSeeder implementations use unique (Order, ModuleName) values (Order 80 for CatalogPricing, Order 85 for CRM).6
