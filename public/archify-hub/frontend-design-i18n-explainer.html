How does SCRIPE-Frontend enforce the Nexus Design System and 100% bilingual EN/AR parity?

Long image

A

Answer

SCRIPE-Frontend mandates 100% @core/ui primitives, the 3-tier Nexus surface hierarchy, flat matte hairline cards, and co-located EN/AR locale dictionaries.1

  1. Every page canvas, card, and nested header maps to --nx-ground, --nx-surface, and --nx-raised so Light and Dark themes switch with zero hardcoded hexes.1
  2. Primary Signal Lime action fills (--nx-accent-fill) always pair with high-contrast dark ink text (text-nx-on-fill), never white text.2
  3. Native HTML form elements (<button>, <input>, <select>, <textarea>) are strictly prohibited across all 65+ feature sub-modules.3
  4. Static UI copy lives exclusively in locales/en.ts and locales/ar.ts and is validated for 100% key parity by scripe validate-locales.4

Why are inline language ternaries strictly banned for static UI copy?

Inline ternaries bypass scripe validate-locales and scatter strings across ViewModels. Only server-persisted fields (labelAr / labelEn) or dir may inspect isAr.5
